# PM Copilot

> AI 기반 PM Workflow Automation Platform

## 1. 프로젝트 개요

### 프로젝트명

PM Copilot

### 한 줄 소개

여러 AI Agent가 협업하여 요구사항 분석부터 PRD, IA, 화면정의서, 일정, WBS까지 생성하는 PM 업무 자동화 플랫폼

### 프로젝트 목표

PM이 반복적으로 수행하는 문서 작성 업무를 자동화하고, 하나의 프로젝트 상태를 기반으로 산출물 간 일관성을 유지하는 AI 기반 Workflow Automation 서비스를 개발한다.

## 2. 문제 정의

- PRD, 요구사항정의서, 화면정의서 등 작성에 많은 시간이 걸린다.
- 프로젝트마다 문서 양식이 달라 반복 작업이 많다.
- 문서 간 내용이 달라지는 문제가 발생한다.
- 요구사항 변경 시 여러 문서를 직접 수정해야 한다.
- PM 경험이 적으면 문서 작성 순서와 필수 내용을 판단하기 어렵다.

## 3. 목표 사용자

- PM 취업 준비생
- Junior PM
- 서비스 기획자
- 스타트업 PM
- 해커톤 참가자
- 사이드 프로젝트 개발자

## 4. 핵심 가치

PM Copilot은 단순한 문서 생성기가 아니라, 프로젝트 정보를 중심으로 PM 업무 흐름과 산출물을 연결하는 AI Workspace이다.

- 문서 작성 자동화
- 문서 간 일관성 유지
- 변경사항 자동 반영
- 반복 업무 최소화
- 사용자 승인 기반의 안정적인 업무 진행

## 5. 입력 방식

### 텍스트 입력

사용자가 프로젝트 정보를 직접 입력한다.

필수 입력 항목:

- 서비스명
- 서비스 설명
- 해결하려는 문제
- 타겟 사용자
- 핵심 기능
- 플랫폼(Web/App)
- 프로젝트 목적

입력 정보가 부족하면 AI가 추가 질문을 통해 프로젝트 정보를 보완한다.

### PDF 업로드

다음 문서를 업로드할 수 있다.

- 기존 기획안
- 회의록

AI는 PDF에서 프로젝트 정보, 요구사항, 의사결정 내용 등을 추출하여 Project JSON에 반영한다.

## 8. System Architecture & Multi-Agent Architecture

PM Copilot은 Workflow Manager를 중심으로 여러 전문 Agent가 협업하는 구조를 사용한다.

```text
사용자
  │ 텍스트 입력 / PDF 업로드 / 승인 / 수정 요청
  ▼
Workflow Manager
  │ 실행 순서·승인·재시도·영향 범위 관리
  ▼
Project JSON (SSOT)
  │ 필요한 데이터만 Agent에 전달
  ├─ Intake Agent
  ├─ Requirement Agent
  ├─ PRD Agent
  ├─ IA Agent
  ├─ Screen Agent
  ├─ API Agent
  ├─ WBS Agent
  ├─ Schedule Agent
  └─ Review Agent
  │ 구조화된 결과 반환
  ▼
Project JSON 업데이트
  ▼
문서 렌더링 및 최종 산출물
```

각 Agent는 하나의 전문 책임을 가지며, Agent 간 직접 통신하지 않는다. Workflow Manager가 실행 순서와 데이터 전달을 통제한다.

## 9. Agent Roles

### 9.1 Intake Agent

- 텍스트 입력 및 PDF 내용 분석
- 프로젝트명, 목표, 문제, 타겟, 핵심 기능 추출
- 누락 정보 식별 및 추가 질문 생성

### 9.2 Requirement Agent

- 사용자 요구사항 구조화
- 기능 요구사항과 비기능 요구사항 분류
- 우선순위 및 MVP 후보 도출

### 9.3 PRD Agent

- 승인된 프로젝트 정보와 요구사항 기반 PRD 생성
- 목표, 문제 정의, 사용자, 기능, 성공 지표 작성

### 9.4 IA Agent

- 기능과 사용자 흐름 기반 IA 생성
- Sitemap 및 메뉴 구조 작성

### 9.5 Screen Agent

- 화면 목록 및 화면별 목적 정의
- 주요 UI 요소, 진입 조건, 상태, 예외 상황 작성

### 9.6 API Agent

- 기능과 화면을 기반으로 API 초안 생성
- 엔드포인트, 메서드, 요청·응답 데이터 구조 정의

### 9.7 WBS Agent

- 기능을 개발 작업 단위로 분해
- 작업 간 선후관계와 담당 영역 정의

### 9.8 Schedule Agent

- WBS, 개발 기간, 팀 구성 정보를 기반으로 일정표 생성
- 주요 마일스톤과 병목 가능성 제시

### 9.9 Review Agent

- 생성된 결과의 누락, 중복, 모순, 용어 불일치 검토
- 문서 간 연결 관계 검증
- 수정이 필요한 항목과 경고 표시

### 9.10 Workflow Manager

- 사용자가 선택한 문서와 실행 모드에 따라 Agent 호출
- 실행 순서 및 승인 상태 관리
- 결과 임시 저장과 공식 반영 제어
- 실패 시 재시도 및 상위 모델 전환
- 변경사항의 영향 범위 분석

## 10. Agent Communication

### 10.1 기본 원칙

각 Agent는 다른 Agent의 문서나 대화 내용을 직접 참조하지 않는다. 모든 Agent는 Workflow Manager를 통해 실행되며, Project JSON을 공통 데이터 저장소이자 Single Source of Truth로 사용한다.

```text
Workflow Manager
        │
        ▼
필요한 Project JSON 데이터 추출
        │
        ▼
Agent 실행
        │
        ▼
구조화된 JSON 결과 반환
        │
        ▼
Schema 검증 및 Project JSON 업데이트
        │
        ▼
사용자 승인 또는 다음 Agent 실행
```

### 10.2 Agent 입력

Workflow Manager는 전체 프로젝트 데이터를 매번 전달하지 않고 Agent 작업에 필요한 데이터만 전달한다.

- PRD Agent: 프로젝트 정보, 문제, 타겟, 요구사항, 기능
- IA Agent: 기능, 요구사항, 사용자 흐름
- Screen Agent: IA, 기능, User Story
- API Agent: 기능, 화면, 데이터 요구사항
- WBS Agent: 기능, 화면, API, 팀 구성, 개발 기간

### 10.3 Agent 출력

Agent는 자유 형식의 결과만 반환하지 않고 사전에 정의된 JSON Schema에 맞춰 결과를 반환한다.

```json
{
  "agent": "requirement_agent",
  "status": "completed",
  "created_items": [],
  "updated_items": [],
  "warnings": [],
  "requires_approval": true
}
```

### 10.4 승인 기반 통신

1. Agent 결과 생성
2. 결과 임시 저장
3. 사용자 검토
4. 승인 시 Project JSON에 확정 저장
5. Workflow Manager가 다음 Agent 실행

사용자가 수정을 요청하면 동일 Agent가 수정 작업을 수행하며, 승인된 결과만 다음 단계의 기준 데이터로 사용한다.

### 10.5 오류 처리

Agent 실행이 실패하거나 JSON Schema 검증을 통과하지 못하면 Workflow Manager가 다음 순서로 처리한다.

- 동일 모델로 재시도
- 프롬프트 보정 후 재시도
- 상위 성능 모델로 전환
- 사용자에게 오류와 수정 필요 사항 표시

### 10.6 변경사항 전달

요구사항 변경 시 모든 Agent를 다시 실행하지 않는다. Workflow Manager가 영향 범위를 분석하고 영향을 받는 Agent만 호출한다.

```text
로그인 기능 삭제
      │
      ▼
Project JSON 수정
      │
      ▼
영향 범위 분석
      ├─ PRD Agent 재실행
      ├─ IA Agent 재실행
      ├─ Screen Agent 재실행
      └─ API Agent 재실행
```

## 11. Project JSON (SSOT)

PM Copilot은 문서를 시스템의 원본으로 사용하지 않는다. 프로젝트의 핵심 정보를 하나의 구조화된 JSON으로 관리하고, 문서는 Project JSON을 렌더링한 결과물로 취급한다.

```json
{
  "project": {},
  "requirements": [],
  "features": [],
  "personas": [],
  "user_flows": [],
  "screens": [],
  "apis": [],
  "schedule": [],
  "wbs": [],
  "documents": [],
  "research": [],
  "data_analysis": [],
  "evidence_refs": [],
  "approvals": [],
  "change_history": []
}
```

이를 통해 다음을 달성한다.

- 문서 간 일관성 유지
- 변경사항 자동 반영
- 중복 생성 방지
- 필요한 데이터만 Agent에 전달
- 토큰 사용량과 생성 시간 절감
- 버전 및 승인 상태 관리

`research`, `data_analysis`, `evidence_refs`는 자료 조사·데이터 분석 모듈을 위한 확장 영역이다. 1차 MVP에서는 빈 배열로 유지하고, 후속 모듈에서 조사 자료와 분석 결과를 저장한다.

## 12. 문서별 독립 생성

모든 문서는 독립적으로 생성할 수 있다.

- PRD만 생성
- IA만 생성
- 화면정의서만 생성
- API 명세만 생성
- WBS와 일정표만 생성

특정 문서가 수정되면 연결된 문서 중 영향받는 문서만 다시 생성한다. 영향이 없는 문서는 재생성하지 않는다.

## 13. 변경사항 자동 반영

사용자가 “로그인 기능을 삭제해줘”라고 요청하면 다음 순서로 처리한다.

1. 변경 요청을 구조화한다.
2. Project JSON을 먼저 수정한다.
3. 영향 범위를 분석한다.
4. 영향받는 Agent만 재실행한다.
5. 사용자 승인 후 관련 문서를 갱신한다.

## 14. 문서 템플릿 및 RAG 적용 여부

초기 버전은 사용자가 직접 등록한 템플릿과 JSON Schema를 기준으로 문서를 생성한다. 검색할 외부 문서가 제한적이므로 MVP에서는 RAG를 사용하지 않는다.

향후 기업별 템플릿과 조직 내부 문서가 늘어나면 RAG 기반 템플릿 검색 기능을 도입할 수 있다.

## 15. AI 모델 운용 전략

작업 난이도에 따라 OpenAI API 모델을 분리하여 사용한다.

- 프로젝트 정보 추출 및 분류: 저비용 모델
- 문서 초안 생성: 저비용 모델
- 복잡한 변경사항 분석: 고성능 모델
- 최종 문서 검수: 고성능 모델
- 단순 수정: 대상 문서 전용 모델 호출

모델명은 운영 환경의 비용, 품질, 속도 기준으로 설정 파일에서 변경할 수 있도록 관리한다.

## 16. 토큰 및 비용 최적화 전략

- Project JSON을 기반으로 필요한 데이터만 전달
- 문서별 독립 생성
- 변경된 문서만 재생성
- 단계별 승인 결과 재사용
- 작업 유형별 모델 분리
- PDF 전체 내용을 매번 전달하지 않고 추출·요약 결과 저장
- 생성 결과와 중간 결과 캐싱

## 18. 시스템 확장성

Agent 인터페이스와 Project JSON Schema를 표준화하여 새로운 문서 유형이나 외부 연동 Agent를 추가할 수 있도록 설계한다.

- 새로운 문서 Agent 추가
- 기업별 템플릿 추가
- 협업 및 댓글 기능 추가
- 버전 비교(Diff) 기능 추가
- Mermaid 다이어그램 및 ERD 생성
- PPT 초안 생성
- GitHub, Jira, Notion 연동

## 19. MCP 기반 외부 서비스 연동 — 향후 확장

MCP(Model Context Protocol)는 MVP 핵심 범위에서 제외하고, 외부 서비스 연동을 위한 확장 기능으로 둔다.

향후 다음과 같은 구조로 도입할 수 있다.

```text
Project JSON
      │
      ▼
외부 연동 Agent
      │
      ▼
MCP Server
      │
      ├─ GitHub Issue 생성
      ├─ Jira Ticket 생성
      ├─ Notion 문서 등록
      ├─ Slack 알림
      └─ Google Drive 저장
```

MCP 연동은 핵심 Workflow와 분리된 어댑터 계층으로 설계하여, MVP 완성 후 필요한 서비스부터 단계적으로 추가한다.
