# PM Copilot

> 자료조사와 의사결정 근거를 실행 가능한 요구사항으로 연결하는 AI 기반 PM Copilot

수정일: 2026-11-02 | 상태: 개발 목표 기획안(현재 구현 범위와 구분)

## 1. 프로젝트 개요

### 프로젝트명

PM Copilot

### 한 줄 소개

조사 근거부터 문제 정의, 요구사항, 제품 의사결정, PRD까지 연결하고 PM의 사고 과정을 검토해주는 근거 기반 PM 업무 자동화 플랫폼

### 프로젝트 목표

PM이 반복적으로 수행하는 문서 작성 업무를 자동화하고, 조사·분석 근거부터 제품 의사결정과 산출물까지의 연결 관계를 관리하며, 주니어 PM이 기획 과정과 판단 근거를 설명할 수 있도록 돕는 AI 기반 Workflow Automation 서비스를 개발한다.

## 2. 문제 정의

- PRD, 요구사항정의서, 화면정의서 등 작성에 많은 시간이 걸린다.
- 프로젝트마다 문서 양식이 달라 반복 작업이 많다.
- 문서 간 내용이 달라지는 문제가 발생한다.
- 요구사항 변경 시 여러 문서를 직접 수정해야 한다.
- PM 경험이 적으면 문서 작성 순서와 필수 내용을 판단하기 어렵다.
- 생성된 요구사항과 기능이 어떤 사용자 문제와 조사 근거에서 나왔는지 설명하기 어렵다.
- AI가 작성한 문서에서 확인된 사실, 가정, 제안이 섞이면 기획의 신뢰도를 판단하기 어렵다.
- 취업 준비생과 주니어 PM은 결과 문서뿐 아니라 조사·판단·우선순위 결정 과정을 포트폴리오로 보여주기 어렵다.

## 3. 목표 사용자

- PM 취업 준비생
- Junior PM
- 서비스 기획자

초기 핵심 사용자는 PM 취업 준비생과 Junior PM으로 한정한다. 스타트업 PM, 해커톤 참가자, 사이드 프로젝트 개발자는 후속 확장 사용자로 둔다.

## 4. 핵심 가치

PM Copilot은 단순한 문서 생성기가 아니라, 조사 근거와 PM의 판단 과정을 제품 요구사항 및 산출물과 연결하는 AI Workspace이다.

- 문서 작성 자동화
- 문서 간 일관성 유지
- 사용자 검토·승인 후 변경사항 반영
- 반복 업무 최소화
- 사용자 승인 기반의 안정적인 업무 진행
- 요구사항별 조사·분석 근거 추적
- 확인된 사실·가정·AI 제안 분리
- 기획 논리와 KPI에 대한 PM 코칭
- 의사결정 이유와 검토 대안 기록
- 기획 과정을 보여주는 포트폴리오 보고서 생성
- 필수 항목·예외·수용 기준까지 구체화한 검토 가능한 문서 초안
- 승인된 요구사항과 연결된 Figma 개발 협업용 와이어프레임 생성

AI는 자료와 대안을 제안하고, 문제 선택·가설 판단·기능 우선순위·문서 확정은 사용자가 결정한다. 조사부터 문서 작성까지 동일한 프로젝트 맥락과 근거 연결을 유지한다.

### 차별화 포지셔닝

> PM Copilot은 문서를 빠르게 생성하는 도구가 아니라, 조사 근거부터 제품 의사결정과 PRD까지 연결해 주는 PM 의사결정 지원 도구다.

일반적인 기획 AI가 PRD, 기능명세, 유저플로우 등 산출물 생성 속도에 집중한다면 PM Copilot은 다음 질문에 답할 수 있게 한다.

- 이 기능은 어떤 사용자 문제에서 출발했는가?
- 요구사항을 뒷받침하는 조사·데이터 근거는 무엇인가?
- AI가 추정한 내용과 사용자가 확인한 사실은 무엇인가?
- 어떤 대안을 검토했고 왜 현재 방향을 선택했는가?
- 요구사항 변경 시 어떤 문서와 결정이 영향을 받는가?

## 5. 입력 방식

### 텍스트 입력

사용자가 프로젝트 정보를 직접 입력한다.

필수 입력 항목:

- 서비스명
- 서비스 설명
- 해결하려는 문제
- 타겟 사용자
- 핵심 기능
- 플랫폼(Web/App)
- 프로젝트 목적

입력 정보가 부족하면 AI가 추가 질문을 통해 프로젝트 정보를 보완한다.

### PDF 업로드

다음 문서를 업로드할 수 있다.

- 기존 기획안
- 회의록

AI는 PDF에서 프로젝트 정보, 요구사항, 의사결정 내용 등을 추출하여 초안으로 저장하고, 사용자 승인 후 Project JSON의 확정 영역에 반영한다.

### 조사 및 분석 입력

- P0: 서비스 아이디어, 조사 질문, 검색 범위, 원문 URL 및 직접 입력한 근거
- P1: 사용자 설문 CSV, 인터뷰 텍스트·PDF, 적법하게 확보한 리뷰 및 커뮤니티 자료
- 업로드 자료는 파일 ID와 페이지·행 등 위치를 보존한다. 개인정보는 분석 전 제거하거나 마스킹한다.
- X·Reddit 등 직접 연동은 접근 권한·API 정책·비용 검토 후 범위를 확정한다. 초기에는 허용된 웹 검색 및 사용자 업로드로 대응한다.

## 7. Workflow

### 전체 자동 생성

프로젝트 입력 → 필요한 Agent 순차 실행 → 문서 초안 일괄 생성 → 사용자 검토·승인 → 확정

전체 자동 생성은 초안 작성의 자동화이며 승인 생략을 의미하지 않는다. 미승인 초안을 이용한 후속 초안은 미확정 상태를 유지한다.

↓

↓

PRD Agent

↓

사용자 승인

↓

IA Agent

↓

사용자 승인

↓

## 8. System Architecture & Multi-Agent Architecture

PM Copilot은 Workflow Manager를 중심으로 여러 전문 Agent가 협업하는 구조를 사용한다.

```text
사용자
  │ 텍스트 입력 / PDF 업로드 / 승인 / 수정 요청
  ▼
Workflow Manager
  │ 실행 순서·승인·재시도·영향 범위 관리
  ▼
Project JSON (SSOT)
  │ 필요한 데이터만 Agent에 전달
  ├─ Intake Agent
  ├─ Research Agent / Evidence Manager
  ├─ Requirement Agent
  ├─ PRD Agent
  ├─ IA Agent
  ├─ Screen Agent
  ├─ API Agent
  ├─ WBS Agent
  ├─ Schedule Agent
  └─ Review Agent
  │ 구조화된 결과 반환
  ▼
Project JSON 업데이트
  ▼
문서 렌더링 및 최종 산출물
```

각 Agent는 하나의 전문 책임을 가지며, Agent 간 직접 통신하지 않는다. Workflow Manager가 실행 순서와 데이터 전달을 통제한다.

## 9. Agent Roles

### 9.1 Intake Agent

- 텍스트 입력 및 PDF 내용 분석
- 프로젝트명, 목표, 문제, 타겟, 핵심 기능 추출
- 누락 정보 식별 및 추가 질문 생성

### 9.2 Requirement Agent

- 사용자 요구사항 구조화
- 기능 요구사항과 비기능 요구사항 분류
- 우선순위 및 MVP 후보 도출

- 사용자 문제별 해결 가설, 검증 방법, 기능 후보 및 MVP 포함·제외 이유 제안
- 사용자 가치·사업 효과·구현 비용·위험 비교 및 부족한 정보 표시

### 9.3 PRD Agent

- 승인된 프로젝트 정보와 요구사항 기반 PRD 생성
- 목표, 문제 정의, 사용자, 기능, 성공 지표 작성
- 요구사항별 승인된 문제·근거·선정 이유·제외 대안·미검증 가설 연결

### 9.4 IA Agent

- 기능과 사용자 흐름 기반 IA 생성
- Sitemap 및 메뉴 구조 작성

### 9.5 Screen Agent

- 화면 목록 및 화면별 목적 정의
- 주요 UI 요소, 진입 조건, 상태, 예외 상황 작성
- 승인된 화면정의서를 기반으로 Figma 와이어프레임 생성용 구조와 개발 전달 주석 작성

### 9.6 API Agent

- 기능과 화면을 기반으로 API 초안 생성
- 엔드포인트, 메서드, 요청·응답 데이터 구조 정의

### 9.7 WBS Agent

- 기능을 개발 작업 단위로 분해
- 작업 간 선후관계와 담당 영역 정의

### 9.8 Schedule Agent

- WBS, 개발 기간, 팀 구성 정보를 기반으로 일정표 생성
- 주요 마일스톤과 병목 가능성 제시

### 9.9 Review Agent

- 생성된 결과의 누락, 중복, 모순, 용어 불일치 검토
- 문서 간 연결 관계 검증
- 문서 유형별 필수 항목, 예외 시나리오, 테스트 가능한 수용 기준, 미결정 사항 확인
- 요구사항과 화면의 대응 관계 및 문서·와이어프레임 간 동작 일치 검토
- 수정이 필요한 항목과 경고 표시

### 9.10 Workflow Manager

- 사용자가 선택한 문서와 실행 모드에 따라 Agent 호출
- 실행 순서 및 승인 상태 관리
- 결과 임시 저장과 공식 반영 제어
- 실패 시 제한된 재시도 및 사용자 설정에 따른 허용 모델 전환
- 변경사항의 영향 범위 분석

### 9.11 Research Agent 및 Evidence Manager

- Research Agent: 시장·경쟁사·사용자 문제 조사, 원문 요약, 반복·상충 의견 및 후속 조사 질문 제안
- Evidence Manager: 출처·정보 유형·검증 상태·승인 상태·연결 ID 관리
- 수집과 AI 해석을 분리하고, 접근 실패·발행일 미상·근거 부족을 명시
- Evidence Manager의 상태 전이와 승인 검사는 서버에서 수행하며 모델의 판단만으로 확정하지 않음

## 10. Agent Communication

### 10.1 기본 원칙

각 Agent는 다른 Agent의 문서나 대화 내용을 직접 참조하지 않는다. 모든 Agent는 Workflow Manager를 통해 실행되며, Project JSON을 공통 데이터 저장소이자 Single Source of Truth로 사용한다.

```text
Workflow Manager
        │
        ▼
필요한 Project JSON 데이터 추출
        │
        ▼
Agent 실행
        │
        ▼
구조화된 JSON 결과 반환
        │
        ▼
Schema 검증 및 초안 저장
        │
        ▼
사용자 승인 또는 다음 Agent 실행
```

### 10.2 Agent 입력

Workflow Manager는 전체 프로젝트 데이터를 매번 전달하지 않고 Agent 작업에 필요한 데이터만 전달한다.

- Research Agent: 프로젝트 정보, 조사 질문, 허용된 검색 범위
- PRD Agent: 프로젝트 정보, 승인된 문제·인사이트·근거·요구사항·기능·결정, 미검증 가설
- IA Agent: 기능, 요구사항, 사용자 흐름
- Screen Agent: IA, 기능, User Story
- API Agent: 기능, 화면, 데이터 요구사항
- WBS Agent: 기능, 화면, API, 팀 구성, 개발 기간

### 10.3 Agent 출력

Agent는 자유 형식의 결과만 반환하지 않고 사전에 정의된 JSON Schema에 맞춰 결과를 반환한다.

```json
{
  "agent": "requirement_agent",
  "status": "completed",
  "created_items": [],
  "updated_items": [],
  "warnings": [],
  "requires_approval": true
}
```

### 10.4 승인 기반 통신

1. Agent 결과 생성
2. 결과 임시 저장
3. 사용자 검토
4. 승인 시 Project JSON에 확정 저장
5. Workflow Manager가 다음 Agent 실행

사용자가 수정을 요청하면 동일 Agent가 수정 작업을 수행하며, 승인된 결과만 다음 단계의 기준 데이터로 사용한다.

### 10.5 오류 처리

Agent 실행이 실패하거나 JSON Schema 검증을 통과하지 못하면 Workflow Manager가 다음 순서로 처리한다.

- 동일 모델로 재시도
- 프롬프트 보정 후 재시도
- 사용자가 허용한 제공자·모델·예산 범위에서 상위 성능 모델로 전환(미허용 시 중단)
- 사용자에게 오류와 수정 필요 사항 표시

### 10.6 변경사항 전달

요구사항 변경 시 모든 Agent를 다시 실행하지 않는다. Workflow Manager가 영향 범위를 분석하고 영향을 받는 Agent만 호출한다.

```text
로그인 기능 삭제
      │
      ▼
변경 초안 생성
      │
      ▼
영향 범위 분석
      ├─ PRD Agent 재실행
      ├─ IA Agent 재실행
      ├─ Screen Agent 재실행
      └─ API Agent 재실행
      │
      ▼
변경 비교 → 사용자 승인 → Project JSON 및 문서 확정
```

## 11. Project JSON (SSOT)

PM Copilot은 문서를 시스템의 원본으로 사용하지 않는다. 프로젝트의 핵심 정보를 하나의 구조화된 JSON으로 관리하고, 문서는 Project JSON을 렌더링한 결과물로 취급한다.

```json
{
  "project": {},
  "requirements": [],
  "features": [],
  "personas": [],
  "user_flows": [],
  "screens": [],
  "apis": [],
  "schedule": [],
  "wbs": [],
  "documents": [],
  "research": [],
  "problems": [],
  "insights": [],
  "validation_plans": [],
  "validation_results": [],
  "drafts": [],
  "data_analysis": [],
  "evidence_refs": [],
  "assumptions": [],
  "decisions": [],
  "coaching_reviews": [],
  "portfolio_exports": [],
  "approvals": [],
  "change_history": []
}
```

이를 통해 다음을 달성한다.

- 문서 간 일관성 유지
- 사용자 검토·승인 후 변경사항 반영
- 중복 생성 방지
- 필요한 데이터만 Agent에 전달
- 토큰 사용량과 생성 시간 절감
- 버전 및 승인 상태 관리

`research`, `data_analysis`, `evidence_refs`는 자료 조사·데이터 분석 모듈을 위한 확장 영역이다. `assumptions`, `decisions`, `coaching_reviews`, `portfolio_exports`는 PM 사고 과정과 기획 품질을 관리한다. P0에서는 웹 검색·요약과 수동 근거 입력을 함께 지원하고 승인된 근거를 요구사항과 연결한다. 통계 분석과 CSV·인터뷰 분석은 P1에서 추가한다. 이 JSON은 목표 논리 구조이며, 기존 저장 형식과의 호환 및 데이터 이관 설계가 필요하다.

모든 문제·근거·인사이트·요구사항·결정에는 고유 ID와 버전을 부여한다. 요구사항은 `problem_ids`, `evidence_ids`, `decision_ids`, `assumption_ids`, `success_metrics`를 통해 연결한다. 초안과 확정본을 분리하고 승인 시 참조 ID·버전 유효성을 검사한다. 근거가 수정·반려되면 기존 문서를 즉시 덮어쓰지 않고 연결된 항목에 재검토 필요 상태를 표시한다.

## 12. 문서별 독립 생성

모든 문서는 독립적으로 생성할 수 있다.

- PRD만 생성
- IA만 생성
- 화면정의서만 생성
- API 명세만 생성
- WBS와 일정표만 생성

특정 문서가 수정되면 연결된 문서 중 영향받는 문서만 다시 생성한다. 영향이 없는 문서는 재생성하지 않는다.

## 13. 변경 영향 분석 및 승인 후 반영

사용자가 “로그인 기능을 삭제해줘”라고 요청하면 다음 순서로 처리한다.

1. 변경 요청을 구조화한다.
2. 확정본을 보존하고 변경 초안을 저장한다.
3. 연결된 정책·화면 흐름·요구사항·문서·결정의 영향 범위를 제안한다.
4. 사용자가 범위를 검토하면 해당 Agent만 실행해 수정안과 변경 비교를 제공한다.
5. 사용자 승인 후 Project JSON과 관련 문서를 같은 버전으로 갱신한다. 반려 시 확정본을 유지한다.
6. 변경 이유·결정자·결정일·이전 버전·영향 항목을 이력에 남긴다.

## 14. 문서 템플릿 및 RAG 적용 여부

초기 버전은 사용자가 직접 등록한 템플릿과 JSON Schema를 기준으로 문서를 생성한다. P0 웹 검색은 외부 검색 결과와 원문을 확인하는 조사 기능으로 제공한다. 별도 내부 문서 벡터 인덱스를 구축하는 RAG는 MVP에서 제외한다.

향후 기업별 템플릿과 조직 내부 문서가 늘어나면 RAG 기반 템플릿 검색 기능을 도입할 수 있다.

## 15. AI 제공자 연결 및 모델 운용 전략

### 사용자 API 키 기반 연결

사용자가 설정 화면에서 API 키를 등록하면 서비스가 연결을 확인하고, 이용 가능한 지원 모델을 선택해 사용할 수 있도록 한다. 연결 대상은 다음 세 제공자다. 이는 제품 개발 요구사항이며 현재 세 제공자가 모두 구현되어 있다는 의미는 아니다.

| 제공자 | 모델 계열 | 제품 내 연결 방식 |
| --- | --- | --- |
| OpenAI | GPT | OpenAI API 키 등록 및 연결 확인 |
| Anthropic | Claude | Anthropic API 키 등록 및 연결 확인 |
| Google | Gemini | Gemini API 키 등록 및 연결 확인 |

세 제공자를 모두 연결할 필요는 없으며 하나만 연결해도 핵심 문서 작성 흐름을 사용할 수 있도록 설계한다. 사용자가 키를 발급·등록한 뒤에는 별도 코드 수정 없이 제공자·모델을 변경할 수 있어야 한다. API 계정·키 발급·결제 설정은 사용자가 수행하며 앱이 자동으로 계정을 생성하거나 유료 이용을 신청하지 않는다.

### 설정 및 사용 흐름

1. 설정에서 제공자를 선택하고 API 키를 입력한다.
2. 연결 테스트로 인증·모델 접근 가능 여부를 확인한다. 유료 요청이 필요한 테스트는 실행 전에 안내한다.
3. 연결된 제공자와 사용 가능한 지원 모델을 표시하고 기본 모델을 선택한다.
4. 프로젝트별 기본 모델 또는 조사·문서 작성·검수 등 작업별 모델을 선택한다.
5. 실제 사용한 제공자·모델·실행 상태·사용량을 결과와 함께 기록한다.
6. 설정에서 키 교체·연결 해제 및 기본 모델 변경을 지원한다.

인증 실패, 사용 한도·결제 문제, 요청 제한, 시간 초과, 지원하지 않는 모델을 구분해 해결 방법을 안내한다. 제공자가 반환하지 않는 정보는 확인 불가로 표시한다. 모델 변경 시에도 Project JSON과 승인 이력은 유지하며, 대화는 작업에 필요한 범위로 요약해 전달한다.

### 작업별 모델 선택 및 자동 전환

- 프로젝트 정보 추출·분류·단순 수정: 품질 기준을 충족하는 저비용 모델 우선
- 상세 문서 초안 작성: 누락·예외·수용 기준 작성 품질을 우선하고 비용·속도를 함께 비교
- 복잡한 변경 영향 분석·최종 검수: 작업에 적합한 고성능 모델
- 기본값은 사용자가 선택한 제공자·모델을 유지
- 자동 선택은 사용자가 활성화한 경우에만, 연결·허용한 모델과 예산 안에서 수행
- 실패 시 재시도 횟수와 대체 모델을 제한하고, 다른 제공자로 전환하려면 사전에 허용한 범위인지 검사
- 대체 모델이 없거나 예산·권한을 초과하면 초안을 보존한 채 중단하고 사용자에게 안내

특정 모델 이름·가격·지원 기능을 고정 가정하지 않는다. 제공자별 지원 목록과 기능 정보를 관리하며 구현 시 공식 문서 및 실제 연결 테스트로 확인한다. 모델 간 문서 품질과 구조화 출력 호환성을 동일한 평가 과제로 검증한다.

### 공통 연결 구조

Workflow Manager → 공통 AI 인터페이스 → OpenAI / Anthropic / Gemini 어댑터 구조를 사용한다. 요청·응답·오류·사용량을 공통 형식으로 변환하고, 제공자별 구조화 출력·파일 입력·검색·도구 호출 지원 차이는 어댑터와 기능 검사로 처리한다. 지원하지 않는 작업은 실행 전에 알리고, 허용된 대체 경로가 있는 경우에만 사용한다.

모든 모델 출력은 동일한 Project JSON Schema와 승인 절차를 통과해야 한다. 웹 검색과 Figma 쓰기 권한은 AI 모델 연결과 별도로 관리하며, 모델 키 등록만으로 외부 서비스 접근이 활성화되지 않는다.

### 키 및 비용 관리

- 키는 서버 측 비밀 저장소에서 관리한다. 로컬 MVP는 환경변수 또는 OS 자격 증명 저장소를 활용하고, 설정 화면에서는 마스킹된 연결 상태만 반환한다.
- 키를 브라우저 영구 저장소, Project JSON, 생성 문서, 대화, 로그에 기록하거나 모델 입력으로 전달하지 않는다.
- 연결 해제 시 저장된 키를 제거하고 해당 제공자의 신규 실행을 차단한다. 제공자 측 키 폐기는 별도 사용자 작업으로 안내한다.
- 외부 제공자에 전송할 자료 범위를 실행 전에 확인할 수 있게 하고, 자동 전환 설정에도 전송 대상 제공자를 명시한다.
- 제공자가 제공하는 사용량과 가격 정보로 추정 비용을 표시하며 미지원·미확인 값은 0으로 간주하지 않는다. 프로젝트별 호출·토큰·비용 한도를 두고 추정치와 실제 청구액을 구분한다.

### 연결 기능 완료 기준

각 제공자에 대해 키 등록 → 연결 확인 → 모델 선택 → 대화 → 구조화된 PRD 생성 → 검수 → 승인 → 다운로드까지 검증한다. 잘못된 키·한도 초과·모델 미지원·시간 초과·키 교체·연결 해제·대체 모델 전환도 확인한다. 모델을 바꿔도 기존 프로젝트와 승인본이 보존되고 비밀 정보가 결과·로그에 노출되지 않아야 한다.

## 19. MCP 기반 외부 서비스 연동 — 향후 확장

MCP(Model Context Protocol)는 MVP 핵심 범위에서 제외하고, 외부 서비스 연동을 위한 확장 기능으로 둔다.

향후 다음과 같은 구조로 도입할 수 있다.

```text
Project JSON
      │
      ▼
외부 연동 Agent
      │
      ▼
MCP Server
      │
      ├─ GitHub Issue 생성
      ├─ Jira Ticket 생성
      ├─ Notion 문서 등록
      ├─ Slack 알림
      └─ Google Drive 저장
```

MCP 연동은 핵심 Workflow와 분리된 어댑터 계층으로 설계하여, MVP 완성 후 필요한 서비스부터 단계적으로 추가한다.

- 자료 업데이트 및 변경점 비교, 근거 변경 시 재검토 알림

- 조사·판단·우선순위 결정 과정을 보여주는 포트폴리오 보고서

### v3 — 확장 플랫폼

## 22. 자료조사 및 분석 상세

### 시장·경쟁사 조사

서비스 아이디어와 조사 질문을 바탕으로 시장 동향 및 유사 서비스를 검색한다. P0에서는 출처가 있는 요약을 제공하고, P1에서는 서비스별 주요 기능·차별점·장단점·관련 사용자 문제를 비교표로 제공한다. 각 항목에 원문 URL, 발행일, 수집일을 연결하고 발행일을 알 수 없으면 ‘미상’으로 표시한다.

### 사용자 문제 조사

공개 커뮤니티·서비스 리뷰·사용자 의견 및 업로드한 설문·인터뷰에서 불편 사례와 요구사항을 분류한다. 반복 문제에는 관측 건수와 자료 범위를 함께 표시하고, 소수 의견을 전체 시장의 수요로 일반화하지 않는다. 커뮤니티 직접 연동은 승인된 접근 범위 내에서만 제공하며 구체적인 제공 범위는 공급자 정책 검토 후 확정한다.

### 조사 결과 분석

- 핵심 내용, 반복 문제, 상충하는 의견, 추가 검증 사항을 구분한다.
- 문제별 원문 근거와 반대 근거를 함께 연결한다.
- AI 해석·해결 가설·후속 조사 방향은 AI_SUGGESTION 또는 ASSUMPTION으로 표시한다.
- 검색 실패나 원문 접근 불가 시 확인한 범위를 밝히고 원문 확인 완료로 표시하지 않는다.
- 조사 횟수·결과 수·시간·비용 한도를 설정하며 실패한 조사만 재시도한다.

## 23. Evidence Manager — 근거 관리

| 유형 | 정의 | 적용 원칙 |
| --- | --- | --- |
| FACT | 확인 가능한 자료로 뒷받침되는 정보 | 원문과 주장의 일치 여부를 검토한다. 리뷰에 의견이 존재한다는 사실과 의견 자체의 진위를 구분한다. |
| ASSUMPTION | 아직 검증되지 않은 가설·추정 | 검증 계획·결과와 연결하고 미검증임을 표시한다. |
| AI_SUGGESTION | AI가 자료를 해석하여 제안한 내용 | 해석에 사용한 근거를 연결하고 사용자 판단을 요청한다. |

### 근거별 필수 관리 항목

- 근거 ID·버전·유형·핵심 주장·원문 발췌 또는 요약
- 원문 URL 또는 업로드 파일 ID와 페이지·행 등 위치
- 자료 발행일(미상 허용), 수집일, 원문 접근 상태
- 연결된 사용자 문제·인사이트·기능 요구사항 ID
- 검증 상태·검증 기록, 승인 상태·승인자·승인일

정보 유형과 검증·승인 상태는 별도로 관리한다. 검증 상태는 `UNVERIFIED / SUPPORTED / CONTRADICTED / INCONCLUSIVE`, 승인 상태는 `DRAFT / IN_REVIEW / APPROVED / REJECTED`로 구분한다. 승인은 기획에 활용하겠다는 결정이며 사실 확인 또는 가설 검증 완료를 뜻하지 않는다. AI의 FACT 분류도 검토 전에는 미검증 초안이다.

승인된 ASSUMPTION은 PRD의 미검증 가설로만 전달하며 확정 사실의 근거로 사용하지 않는다. 반려된 근거는 이력에 보존하되 신규 요구사항의 채택 근거에서 제외한다. 승인 후 내용을 수정하면 새 버전을 만들고 재승인을 요청한다.

## 24. 문제 정의·가설 검증·MVP 결정

### 문제 정의

문제별로 타깃 사용자, 발생 상황, 불편과 영향, 중요성, 해결 필요성, 관련 근거를 정리한다. AI가 도출한 문제와 인사이트는 사용자가 승인·수정·반려할 수 있다.

### 가설 검증 지원

해결 가설에 인터뷰 질문, 설문 또는 사용성 테스트 방법, 대상 사용자, 확인할 항목, 판단 지표·기준을 제안한다. 실제 수행 기록·결과 자료·사용자의 판단이 있어야 검증 결과를 확정한다. 결과가 없거나 표본이 부족하면 미검증 또는 판단 보류로 유지하며, AI 분석이나 인사이트 승인만으로 검증 완료 처리하지 않는다.

### 기능 우선순위 및 MVP

| 비교 항목 | 기록 내용 |
| --- | --- |
| 사용자 가치 | 해결하는 문제와 기대 효과, 연결 근거 |
| 사업 효과 | 목표 지표와 예상 영향, 추정의 전제 |
| 구현 비용 | 개발·운영 공수의 추정과 산정 근거 |
| 위험 | 기술 의존성·데이터 접근·검증 부족 |
| 최종 결정 | MVP 포함·제외·보류, 선정·제외 이유, 결정자 |

정보가 없는 항목은 ‘미확인’으로 표시하고 추가 조사나 담당자 확인을 제안한다. AI 추천 순위와 사용자의 최종 순위를 구분하며, 사용자가 최종 범위를 확정한다.

## 25. Research → PRD 및 Decision Log

1. 자료조사 실행 및 출처 수집
2. 사용자 문제·인사이트 초안 도출
3. 관련 근거·반대 의견·미검증 가정 검토
4. 사용자 인사이트 승인·수정·반려
5. 승인된 내용을 기반으로 기능 요구사항 제안
6. 사용자 기능 선택 및 근거·제외 대안·판단 이유 기록
7. 최종 요구사항 승인 후 PRD 반영

PRD의 각 요구사항에는 해결할 문제, 관련 근거, 선택 이유, 제외 대안, 미검증 가설, 성공 지표를 연결한다. 사용자는 요구사항에서 인사이트·근거를 거쳐 원문이나 업로드 위치까지 확인할 수 있어야 한다. 근거가 없는 요구사항은 근거 부족을 표시하고 사용자가 가정 기반 채택임을 명시하도록 한다.

Decision Log에는 해결할 문제, 검토 선택지, 최종 선택, 근거 ID, 제외 대안과 이유, 결정자·결정일, 관련 요구사항, 변경 이유 및 이전 결정 버전을 기록한다. 과거 결정은 덮어쓰지 않고 후속 결정과 연결한다. 기본 기록은 P0, 자동 변경 영향 분석은 P2 범위다.

## 26. Figma 개발 협업용 와이어프레임

### 목표 및 범위

승인된 요구사항·IA·User Flow·화면정의서를 바탕으로 **Figma에서 편집 가능한 개발 협업용 와이어프레임을 생성**한다. 단순 링크 등록이나 연동 가능성 검토를 넘어 P1의 명시적 산출물로 둔다. 초기 범위는 정보 구조와 기능·동작 전달에 필요한 저충실도 와이어프레임이며, 브랜드 비주얼 완성·최종 UI 디자인·운영 코드 생성은 별도 범위다.

### 생성 내용

- 화면 목록, 화면 ID, 목적, 사용자 역할, 진입 조건, 연결 요구사항 ID
- 주요 화면의 콘텐츠 계층, 내비게이션, 입력 폼, 목록·상세, 버튼·모달 등 요소 배치
- 기본·로딩·빈 데이터·오류·성공·권한 제한 상태 중 해당 화면에 필요한 상태
- 입력값 형식·필수 여부·유효성 검사·오류 문구·버튼 활성 조건
- 사용자 행동별 이동·저장·취소·뒤로 가기 동작과 예외·복구 경로
- 핵심 사용자 흐름의 화면 간 연결 및 시작·종료 지점
- 데이터 항목·읽기/쓰기 동작·관련 API 초안 참조; 미정 API는 확인 필요로 표시
- 목표 플랫폼·화면 크기·반응형 규칙과 키보드 이동·레이블 등 접근성 요구
- 개발 전달 주석, 미결정 사항, 승인 상태, 기준 문서 버전

텍스트와 UI 요소는 편집 가능한 프레임·레이어로 구성하고 반복 요소는 재사용 가능한 컴포넌트로 관리한다. 기존 디자인 시스템이 지정된 경우 해당 자산을 우선 활용한다. 세부 API 경로·필드·동작을 근거 없이 확정하지 않는다.

### 생성·검토 흐름

1. 승인된 요구사항과 화면정의서의 필수 정보·누락 사항을 확인한다.
2. 화면 목록·상태 목록·핵심 흐름을 제안하고 사용자가 생성 범위를 승인한다.
3. 사용자가 지정한 Figma 파일 또는 새 파일에 와이어프레임 초안을 생성한다.
4. 화면별 요구사항·동작·예외 주석과 문서 링크를 연결한다.
5. 레이아웃 깨짐, 텍스트 잘림, 흐름 단절, 상태 누락, 요구사항 불일치를 검수한다.
6. 사용자가 수정·승인한 버전을 개발 전달 대상으로 확정한다.

요구사항 ID ↔ 화면 ID ↔ Figma 파일·노드 ID·기준 버전의 대응 관계를 저장한다. 기존 디자인은 자동 덮어쓰지 않으며, 변경 초안과 비교 내용을 승인 후 반영한다. Figma에서 직접 수정한 내용의 자동 역동기화는 P2 검토 범위로 두고 P1에서는 변경 사실과 기준 문서 불일치를 사용자가 기록할 수 있게 한다.

### 구현 및 완료 기준

Figma 생성 경로, 사용자 인증·파일 쓰기 권한, 편집 가능한 요소 생성 지원 범위, 호출 제한과 비용을 P1 개발 착수 전에 검증한다. 제품 기능은 특정 개발 환경의 도구 사용 가능 여부만으로 구현 완료로 간주하지 않는다. 연동 실패 시 재시도 가능한 상태와 미생성 화면 목록을 제공하며, 화면정의서만 출력한 결과를 Figma 생성 완료로 표시하지 않는다.

선정된 MVP의 화면을 가진 요구사항은 모두 하나 이상의 화면에 연결되어야 한다. 화면이 필요 없는 요구사항은 사유를 기록한다. 주요·예외 흐름을 따라갈 수 있고, 필요한 상태·동작·개발 주석이 존재하며, 개발자가 Figma에서 요소를 편집하고 연결 문서를 확인할 수 있을 때 전달 가능한 초안으로 판정한다. 미결정 사항이 개발을 막는 경우 ‘개발 전달 준비 완료’로 표시하지 않는다.

P2에서는 클릭 가능한 프로토타입의 인터랙션 고도화, 피드백 분석, 요구사항 수정안 연결 및 변경 동기화를 확장한다.

## 27. 기존 기능 중복 및 구현 가능성 검토

아래 평가는 현재 저장소를 기준으로 한 설계 판단이다. 외부 API 정책·가격·권한은 이번 수정에서 확인하지 않았으므로 연동 확정 사항으로 간주하지 않는다.

| 제안 | 기존 기획과의 관계 | 반영 및 구현 과제 |
| --- | --- | --- |
| 웹 검색·요약 | 기존 v2 자료조사 모듈 | P0로 이동. 검색 공급자 선정, 원문 확인, 인용 저장, 비용 한도 구현 필요 |
| 근거 분류·출처 | 기존 evidence_refs·assumptions | 새 모듈 중복 생성 대신 기존 모델 확장. 유형·검증·승인 상태 분리 |

| 경쟁사·설문·인터뷰 분석 | 기존 v2 조사·데이터 분석 | P1로 구체화. CSV 파싱·열 매핑·행 추적·개인정보 처리 필요 |

| Decision Log | 기존 decisions | P0 기록 필드 구체화. 선택·제외 이유와 변경 버전 보존 |
| 변경 영향 분석 | 기존 Workflow Manager·문서 재생성 | P2 유지. 연결 ID와 버전 기반 영향 분석, 변경 비교·승인 적용 필요 |
| Figma 와이어프레임 생성 | 기존 화면·흐름·프로토타입 연계 구체화 | P1에서 편집 가능한 화면·상태·동작 주석 생성. 인증·쓰기 경로 검증 필요. 고도화·동기화는 P2 |
| 다중 AI 제공자 연결 | 기존 OpenAI 모델 선택 확장 | P0에 Claude·GPT·Gemini 공통 어댑터·키 설정·연결 검사 추가. 제공자별 지원 기능과 구조화 출력 검증 필요 |
| 문서 초안 완성도 | 기존 문서 생성·Review Agent | P0 PRD부터 필수 항목·예외·수용 기준 검수. 확장 문서에도 동일 원칙 적용 |
| 문서·코칭·포트폴리오 | 기존 핵심 및 확장 기능 | 삭제 없이 유지. 조사 → PRD 완성 후 순차 개발 |

현재 PRD 생성 경로는 승인 전에 프로젝트의 기능·요구사항을 갱신한다. P0에서는 생성 결과를 초안 영역에 저장하고, 승인 시에만 확정 기능·요구사항을 갱신하도록 수정해야 한다. PDF 업로드는 현재 텍스트 추출·저장 단계이므로 승인된 근거 추출 및 요구사항 연결은 추가 구현 대상이다.

JSON 파일 저장은 단일 사용자 MVP에서 유지하되 참조 무결성·버전 충돌 검사와 저장 실패 시 일관성 보장이 필요하다. 다중 사용자·공동 편집은 기존 계획대로 데이터베이스·권한 체계 도입 후 확장한다.

아래 기준은 제품 검증 계획이며 측정 완료 결과가 아니다. 정량 목표는 초기 사용자 테스트에서 기준선을 측정한 뒤 확정한다.

## 29. 문서 초안 완성도 기준

### 좋은 초안의 정의

사용자가 문서를 처음부터 다시 쓰지 않고, 근거·선택·미결정 사항을 검토해 수정할 수 있는 구체적인 초안을 제공한다. 항목 제목이나 일반적인 설명만 채운 문서는 완성된 초안으로 간주하지 않는다. 누락 방지는 문서별 체크리스트와 시나리오 검수로 관리하며 모든 정보를 안다는 전제로 빈칸을 추정해 채우지 않는다.

### 문서별 필수 내용

| 문서 | 반드시 검토할 내용 |
| --- | --- |
| PRD | 배경·목표·비목표, 타깃·문제·근거, 범위·제외 이유, 핵심 흐름, 기능·비기능 요구사항, 우선순위, 성공 지표·측정 방법, 가정·위험·의존성·미결정 사항 |
| 요구사항·기능 정의서 | 고유 ID, 목적·문제·근거, 사용자·권한, 사전 조건·트리거, 입력·처리·출력, 정상·대안·오류 흐름, 업무 규칙, 데이터, 수용 기준, 우선순위·연관 항목 |
| MVP 정의 | 검증할 가치·가설, 포함·제외·보류 기능과 이유, 핵심 사용자 여정, 의존성, 출시 판단 기준·성공 지표 |
| User Story | 사용자 역할·목표·가치, 연결 요구사항, 사전 조건, 테스트 가능한 수용 기준과 예외 |
| IA·Sitemap·User Flow | 정보 계층·화면 목록, 진입·종료, 이동·분기, 권한별 경로, 실패·복구 흐름, 화면·요구사항 ID |
| 화면정의서 | 화면 목적·진입 조건, 요소·데이터, 입력 규칙·문구, 행동·전이, 로딩·빈 화면·오류·성공·권한 상태, 반응형·접근성, 요구사항 참조 |
| API 명세 초안 | 목적·연관 요구사항, 메서드·경로 후보, 인증·권한, 요청·응답·오류 예시, 검증 규칙, 목록 조회·중복 처리 등 해당 조건, 개발 확인 사항 |
| WBS·일정표 | 작업 범위·완료 조건, 선후관계·의존성, 담당 역할, 공수 산정 근거·불확실성, 마일스톤, 위험·검토 일정 |

기능에 따라 개인정보·보안·성능·접근성·운영·분석 이벤트·삭제 및 보존 정책도 검토한다. 적용되지 않는 항목은 이유를 기재하고, 아직 결정하지 않은 항목과 구분한다. 성공 지표에는 정의·측정 방법·목표값을 기록하되 목표값의 근거가 없으면 제안 또는 미정으로 표시한다.

### 생성 및 검수 절차

1. 입력 자료를 구조화하고 문서 유형별 필수 정보와 비교한다.
2. 핵심 범위·권한·업무 규칙처럼 결과를 크게 바꾸는 정보부터 사용자에게 질문한다. 나머지는 가정·미결정 사항으로 드러낸다.
3. 승인된 정보로 상세 초안을 작성하고 각 요구사항에 근거와 수용 기준을 연결한다.
4. Review Agent가 필수 항목 누락, 모순·중복, 모호한 표현, 예외 누락, ID 연결과 문서 간 일관성을 확인한다.
5. 기존 근거로 해결 가능한 누락은 보완하고, 판단이 필요한 항목은 질문·확인 담당·영향 범위로 정리한다. 자동 보완 횟수에는 한도를 두고 남은 문제를 공개한다.
6. 사용자에게 초안·검수 결과·미결정 목록을 함께 제공하고 승인 후 확정한다.

### 초안 통과 기준

- 필수 항목은 구체적으로 작성하거나 미정·적용 제외 및 사유가 명시되어 있다.
- 각 기능에는 입력·처리·결과와 테스트 가능한 수용 기준이 있고 필요한 예외가 포함되어 있다.
- ‘빠르게’, ‘편리하게’, ‘적절하게’ 등 판정할 수 없는 표현만으로 완료 기준을 작성하지 않는다.
- 승인된 내용과 가정·AI 제안이 구분되며, 문서 간 용어·ID·권한·상태·범위가 일치한다.
- 해결되지 않은 누락·모순과 개발을 막는 결정 사항이 보이며, 이를 숨긴 채 검수 완료로 표시하지 않는다.
- 문서 초안 작성 완료와 개발 착수 가능 상태를 구분한다. 후자는 차단 사항 해결과 사용자 승인을 요구한다.

## 30. 수정 원칙 및 출처

1. 검색 결과의 양보다 기획에 필요한 근거를 우선한다.
2. 확인 가능한 사실, 미검증 가정, AI 해석을 구분한다.
3. 조사 결과를 문제 정의·기능 요구사항·PRD까지 연결한다.
4. AI는 제안하고 사용자가 최종 결정한다.
5. 채택한 기능과 제외한 대안의 이유를 함께 보존한다.
6. 초기에는 핵심 흐름을 완성하고 복잡한 자동화는 후속 단계로 분리한다.

최종 목표는 **자료조사 결과와 기획 의사결정의 근거를 연결하고, 실행 가능한 요구사항과 산출물로 구체화하도록 지원하는 AI 서비스기획 도구**다.
